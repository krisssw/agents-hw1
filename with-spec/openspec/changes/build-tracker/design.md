# Design

## Context

Проект пустой (greenfield): в корне только `brief.md` и каталог OpenSpec, кода и тестов нет. Мотивация и границы — см. proposal.md; требования — см. specs/tracker/spec.md. Ограничения: без внешних библиотек, CDN и сборки; тесты — встроенный `node:test` (Node 22); логика должна тестироваться в Node без DOM.

## Goals / Non-Goals

**Goals:**
- Отделить предметную логику (`domain.mjs`, чистые функции без DOM и глобального состояния) от интерфейса (`app.mjs`).
- Сделать расчёты, фильтрацию и валидацию детерминированными и покрытыми тестами T1–T5.
- Гарантировать отсутствие NaN/Infinity в любом состоянии.

**Non-Goals:**
- Фреймворки, виртуальный DOM, роутинг, сборщики.
- Автоматическое тестирование DOM/браузера (ручная проверка).

## Decisions

### D1. Формат задачи
```
{ id: string, title: string, hours: number, done: boolean }
```
- `title` хранится уже после trim; `hours` — число (не строка), кратное 0,5.
- `id` генерируется функцией-генератором, которую можно подменить в тестах (по умолчанию `crypto.randomUUID()` при наличии, иначе счётчик + время). Стартовые задачи имеют фиксированные id (`t1`, `t2`, `t3`) для предсказуемости тестов.
- Состояние приложения: `{ tasks: Task[], filter: 'all' | 'active' | 'done' }`.
- Альтернатива: хранить часы строкой из формы — отклонена, т.к. ломает суммирование и сравнение.

### D2. Чистые функции в `domain.mjs`
Все функции не мутируют аргументы и возвращают новые значения:
- `createInitialTasks()` → новый массив стартовых задач (копия при каждом вызове).
- `addTask(tasks, {title, hours}, makeId)` → новый массив с задачей `done=false` (вызывается только после успешной валидации).
- `removeTask(tasks, id)` → массив без задачи; неизвестный id — массив без изменений.
- `toggleTask(tasks, id)` → массив, где у задачи инвертирован `done`.
- `computeMetrics(tasks)` → `{ count, totalHours, doneHours, progress }`, где `progress = totalHours > 0 ? Math.round(100 * doneHours / totalHours) : 0`.
- Альтернатива: классы с мутируемым состоянием — отклонена: чистые функции проще тестировать и исключают скрытые побочные эффекты.

### D3. Фильтрация отдельно от метрик
- `filterTasks(tasks, filter)` возвращает только видимое подмножество; `computeMetrics` всегда получает полный `state.tasks`.
- В `app.mjs` рендер вызывает обе функции независимо: `render(state) → list(filterTasks(state.tasks, state.filter)) + summary(computeMetrics(state.tasks))`. Так фильтр физически не может повлиять на метрики (R4, T3).
- Неизвестное значение фильтра трактуется как `'all'`.

### D4. Валидация
`validateTaskInput({ title, hours })` принимает сырые строки из формы и возвращает `{ ok: true, value: { title, hours } }` или `{ ok: false, errors: { title?, hours? } }`.
- Название: `String(title).trim()` должен быть непустым.
- Часы: сначала `trim`; пустая строка → ошибка «Укажите количество часов» (не 0). Запятая заменяется на точку (поддержка «0,5»). Затем `Number(...)`: должно быть `Number.isFinite`, `0.5 ≤ h ≤ 24`, `Number.isInteger(h * 2)`.
- Обе ошибки собираются одновременно, чтобы показать их у обоих полей.
- В UI: при ошибке форма не очищается, текст ошибки выводится в элементе рядом с полем (`aria-describedby`, `aria-invalid="true"`); при успехе форма сбрасывается и ошибки скрываются. Атрибуты `min/max/step` на `<input>` — только подсказка, источник истины — `validateTaskInput` (форма с `novalidate`, чтобы показывать свои сообщения).

### D5. Пустое состояние
- `computeMetrics([])` → `{ count: 0, totalHours: 0, doneHours: 0, progress: 0 }` за счёт явной проверки делителя.
- UI показывает сообщение «Задач нет — добавьте первую» при пустом полном списке и «Нет задач для этого фильтра» при пустом отфильтрованном; форма остаётся активной.

### D6. Интерфейс и вёрстка
- `index.html` подключает `styles.css` и `<script type="module" src="app.mjs">`; `app.mjs` импортирует `domain.mjs`.
- Делегирование событий на списке (`data-id`, `data-action="toggle|remove"`); статус — `<input type="checkbox">` с label, удаление — `<button>` с `aria-label="Удалить «…»"`; фильтр — группа радиокнопок или `<select>` с подписью.
- Mobile-first CSS: `box-sizing: border-box`, `max-width: 100%`, flex-wrap, переносы длинных названий (`overflow-wrap: anywhere`), без фиксированных ширин > 390 px.
- Прогресс выводится текстом («25%») и элементом `<progress>`/полосой с подписью.

### D7. Необязательное хранилище
- Отдельный адаптер `loadTasks/saveTasks` в `app.mjs` с `try/catch`; данные проверяются при чтении (массив задач с корректными полями), иначе используется стартовый набор.
- При исключении — баннер «Сохранение недоступно, данные хранятся только до закрытия страницы», работа продолжается в памяти.

### D8. Тесты
- `tests/acceptance.test.mjs` импортирует только `domain.mjs` и проверяет T1–T5 через `node:test` и `node:assert/strict`; запуск `node --test tests/acceptance.test.mjs`.
- Форма, кнопки, тексты ошибок, узкий экран — ручная проверка по чек-листу tasks.md.

## Risks / Trade-offs

- [Chrome блокирует ES-модули при открытии через `file://` (CORS)] → в инструкции указать запуск локального статического сервера из стандартного окружения, например `python3 -m http.server`, и описать ограничение; логика остаётся проверяемой тестами в Node.
- [localStorage через `file://` ведёт себя по-разному в браузерах (общий origin, запрет, очистка)] → хранилище необязательно, ошибки перехватываются, работа продолжается в памяти.
- [Ошибки плавающей точки при суммировании] → часы кратны 0,5 и точно представимы в двоичном виде; прогресс округляется `Math.round`.
- [Расхождение UI-валидации браузера и доменной] → `novalidate` на форме, единственный источник истины — `validateTaskInput`.
- [Ручные проверки субъективны] → чек-лист с конкретными ожиданиями; в отчёте фактически выполненные проверки перечисляются отдельно от предложенных, запуск браузера не заявляется, если его не было.
